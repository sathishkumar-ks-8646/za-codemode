Code Mode · Chapter 00

Start here

Your AI agent can already talk to Zoho Analytics one call at a time. This tool lets it write one program instead — with loops, filters and arithmetic — and run it in a sealed sandbox right next to the API.

It is built on the UTCP code-mode engine: the operation catalog is a UTCP manual generated from the published OpenAPI specifications, and the program runs in a V8 isolate with those operations bridged in. Your agent speaks MCP and never sees any of that — see How the engine works.

Ten minutes, nothing to host

Clone it, store your credentials, and add one block to your agent's configuration file. There is no server to deploy, no port to open, and no AI model to supply — your agent brings its own. Jump to Install & configure.

01Is this for you?

Yes, if…

…you use an MCP-capable agent — Claude Desktop, Claude Code, Cursor, VS Code, Windsurf — and you want it to answer questions that span more than one call: totals across workspaces, exports that must be polled to completion, or anything needing a loop.

Probably not, if…

…you only need single lookups like "list my workspaces". The Zoho Analytics MCP Server already does that with named tools, and a named tool is cheaper and clearer for one-shot work. The two are designed to sit side by side — see How this relates to the MCP Server.

02The idea in sixty seconds

Ask an agent "what were East-region sales since July, across every workspace?" and a conventional tool-calling setup has to make a round trip per step:

ApproachWhat happensModel turns
One tool call per turnlist workspaces → list views → start export → poll → poll → poll → download → repeat per view, then add the numbers up in the model's head19
One programthe model writes a loop that does all of it in the sandbox and returns four numbers1

Both make the same API calls. The difference is that the intermediate data — every row, every JOB IN PROGRESS poll — never reaches the model.

Four tools, no matter how large the API is:

06The four things to know before you start

  1. It does not reduce API units. The same calls are made, so the same units are billed. What it saves is model turns and context.
  2. Write operations are off by default, and you can narrow further. 76 read-only operations are exposed out of 203, and ZA_DOMAINS restricts that to the API domains you actually need. See Choosing what to expose.
  3. Your agent's model writes the code. A more capable model writes better code. If results are poor, that is the first thing to check.
  4. It will not guess which table you meant. When two views both match your words, it returns both and asks. See Finding your data.

Code Mode · Chapter 01

What it is

An MCP server that gives your AI agent four tools: one to find your data, one to find API operations, one to read how they work, and one to run code against them.

Under the MCP surface it is UTCP code mode — a UTCP manual of 203 operations generated from the published OpenAPI specifications, executed by @utcp/code-mode in a V8 isolate. Chapter 08 covers that in full; this chapter is about what it does.

The model's code runs in a V8 isolate. It cannot open a socket, read a file or import a module. When it calls za.exportDataView(...), that is not an HTTP request — it is a callback out of the isolate into the server process, which makes the real call with credentials the sandbox never sees.

02The four tools

find_analytics_objects

The first problem is not which endpoint — it is which table. A user says "my profit table" and the table is called Sales_Profit_by_Country. A model left to itself writes viewName === 'profit', matches nothing, and reports that the table does not exist.

So names are resolved before code is written:

> find_analytics_objects("profit")

{ "found": true, "confident": false,
  "best": { "viewName": "Profit Margin Trend", "viewType": "Chart",
            "score": 88, "matchedOn": "name starts with the query" },
  "alternatives": [ { "viewName": "Sales_Profit_by_Country", "viewType": "Table",
                      "score": 75, "matchedOn": "name contains the query" } ],
  "searchedWorkspaces": 4, "totalWorkspaces": 4,
  "ambiguous": "Several views match. Report these to the user and let them choose..." }

Three properties matter more than the matching itself:

  • It says why it matched, so a weak hit is visible as one.
  • It refuses to guess. Two candidates both containing your word means confident: false and both returned — because silently analysing the wrong table is worse than asking.
  • A miss reports the scope. "Nothing matched in 4 of 4 workspaces", with the workspace list — never a bare "your data does not exist".

It searches workspaces, views, columns, variables, folders, groups, datasources and aggregate formulas — everything except workspaces and views is scoped to one workspace, because that is where they live.

And when you name something, it resolves or it stops:

> "use the variable sum"        -> sum_of_cost          (prefix match, resolved)
> "use the variable headcount"  -> STOPPED: no variable matching "headcount".
                                   Available: sum_of_cost, region_filter, fiscal_year_start.
> "use the variable sum"        -> STOPPED: ambiguous — sum_of_cost (88),
  (workspace has two)              sum_of_revenue (88). Ask the user which.

Substituting a different variable than the one you named produces a confident wrong number, so it is never done. The refusal is enforced by the server: a program that catches it and carries on anyway still fails.

search_analytics_api

There are 203 operations. Describing all of them to a model would cost roughly 145,000 tokens, so the server never does. Instead the agent describes its task and gets back only what matches:

> search_analytics_api("export rows from a view with a filter")

4 matching operations. Call them on the `za` object inside run_analytics_code.
`ORG_ID` is predefined there, so pass it as `'ZANALYTICS-ORGID': ORG_ID`.

// Export Data from a View
await za.exportDataView({
  "ZANALYTICS-ORGID": string;
  "workspace-id": string;
  "view-id": string;
  "CONFIG"?: string;   // Configuration that filters and formats the export...
});
...

Under a thousand characters instead of 145,000 tokens.

get_analytics_guide

Signatures say what to call. They do not say that criteria strings use a particular SQL-like grammar, that CONFIG must be stringified, or that a bulk export is three calls and a poll. That knowledge comes from the Zoho Analytics documentation, and it ships with the server:

ContentCount
Multi-step playbooks8
Reference topics9
Documented error codes385
> get_analytics_guide("filter-criteria-syntax")   // a reference, by id
> get_analytics_guide("how do I export a large table")   // a question
> get_analytics_guide("8080")   // an error code

Two things happen without the agent asking. Search results for export-job operations end with a pointer to the asynchronous-export playbook, and any error code in a failed run is annotated with its documented meaning and resolution.

run_analytics_code

The agent writes plain JavaScript and the server runs it:

const ws = await za.getOrgWorkspaces({ 'ZANALYTICS-ORGID': ORG_ID });
let total = 0;

for (const w of ws.data.workspaces) {
  const views = await za.getViews({
    'ZANALYTICS-ORGID': ORG_ID, 'workspace-id': w.workspaceId, CONFIG: '{}',
  });
  for (const v of views.data.views.filter((v) => v.viewName.includes('Sales'))) {
    const out = await za.exportDataView({
      'ZANALYTICS-ORGID': ORG_ID, 'workspace-id': w.workspaceId, 'view-id': v.viewId,
      CONFIG: JSON.stringify({ responseFormat: 'json', criteria: `"Sales"."Region"='East'` }),
    });
    total += rows.sum(rows.of(out), 'Sales').total;
  }
}

return { total };

One tool call. The rows stay in the sandbox; only { total } comes back.

02Step 1 — Get your Zoho credentials

Two values, both from Zoho, both needed before the tool is any use.

Your Organization ID

In Zoho Analytics, go to Settings → Organization. Copy the ID — a long number like 2375824000000000001. Every call this tool makes is scoped to it.

An OAuth credential

A Self Client is the right kind here: it is for a program acting as you, with no browser sign-in.

  1. Go to api-console.zoho.com and sign in with the account that owns the data.
  2. Choose Add Client → Self Client → Create.
  3. Copy the Client ID and Client Secret.
  4. Open the Generate Code tab and enter the scopes you need — see below.
  5. Set a validity of 10 minutes, give it a description, and click Create.

Copy the generated code immediately: it is shown once and it expires in minutes. You will paste it in step 3, which exchanges it for a refresh token.

Use a Self Client made for this tool alone

Then revoking it stops this tool and nothing else. Reusing a credential that other integrations share means you cannot withdraw access from one without breaking the rest.

03Which scopes

The authoritative list is Zoho's

Scopes are an Analytics API concept, not something this tool defines, and the set grows. Read Authentication in the API documentation and choose from there. What follows is orientation, not a substitute.

A scope is ZohoAnalytics.<family>.<operation>, where <operation> is one of read, create, update, delete or all. Supply them to Generate Code as a comma-separated list:

ZohoAnalytics.metadata.read,ZohoAnalytics.data.read,ZohoAnalytics.modeling.read

The families:

FamilyCovers
metadataOrganizations, workspaces, views, folders, trash, dependents
dataRow data: import, export, add, update and delete rows, sync and refetch
modelingSchema objects: tables, columns, lookups, query tables, formulas, variables
shareSharing, publishing, private and public URLs, slideshows, groups, workspace users
embedEmbed URLs, for Embedded Analytics (OEM) customers
usermanagementOrganization users, roles, subscription and resource usage
fullaccessEverything above — ZohoAnalytics.fullaccess.all

Three sets that match how this tool is actually used:

You want to…Grant
Read and analyse, nothing moreZohoAnalytics.metadata.read, ZohoAnalytics.data.read, ZohoAnalytics.modeling.read
Also build tables, reports and formulasadd ZohoAnalytics.modeling.all, ZohoAnalytics.data.all
Not think about itZohoAnalytics.fullaccess.all
fullaccess.all is the wrong default for this tool

It is the simplest answer and the wrong one here. This server executes code written by a language model, and the OAuth grant — not ZA_ALLOW_WRITES — is the real boundary: the flag is a setting on your own machine, while the grant is enforced by Zoho. A read-only grant means a misread prompt cannot delete a workspace, whatever the model writes or the configuration says.

Grant it only when you have a reason. See Security.

A missing scope surfaces late

An access token without the scope an operation needs fails with error 8535, at the moment your agent makes the call — not at setup. Ask your agent get_analytics_guide("8535") if you see it. If you widen what the server may reach with ZA_DOMAINS or ZA_ALLOW_WRITES, check the grant still covers it.

Code Mode · Chapter 03

Using it

You do not call the tools yourself. You ask your agent a question, and it decides to use them. This chapter is about asking well.

01The normal flow

Every task follows the same shape, and your agent does it on its own:

  1. find_analytics_objects — whenever you name a table, view or workspace, it resolves that name to a real ID first.
  2. search_analytics_api — it describes the operation it needs and gets back signatures.
  3. get_analytics_guide — optional, when it needs to know how something behaves.
  4. run_analytics_code — it writes a program and gets back the result.

02Finding your data

This is the step people expect to be the fragile one, so it is worth seeing.

You name something that does not quite exist. You say "analyse my profit table"; the table is called Sales_Profit_by_Country. The name is resolved by fuzzy match, and because Profit Margin Trend also matches, both come back and your agent asks which you meant rather than picking one.

You name nothing at all. You say "do sales analysis on my data". Your agent lists your workspaces, ranks views matching "sales", and analyses what it finds — reporting which workspaces it looked in:

{ "analysed": [
    { "workspace": "Sales Data", "view": "Sales Q3", "rows": 5, "column": "Sales", "total": 50900 },
    { "workspace": "Marketing",  "view": "Sales Funnel", "rows": 3, "column": "Sales", "total": 11100 } ],
  "searched": "4/4" }

You name something exactly. You say "use the variable sum" and the variable is sum_of_cost. It resolves — a prefix match is good enough.

Nothing matches, so it stops. This is the important one. If you name a variable, column, table or folder and nothing matches it, the operation halts. It does not fall back to whatever else is in the workspace:

STOPPED: no variable matching "headcount". Do not substitute another variable.
Available variables: sum_of_cost, region_filter, fiscal_year_start.
Report this to the user and ask which they meant.

Two things match, so it also stops. If the workspace has both sum_of_cost and sum_of_revenue, "the sum variable" is ambiguous and you are asked which — rather than one being chosen for you.

Substitution is the failure this prevents

Analysing sum_of_revenue when you asked for sum_of_cost produces a confident, plausible, wrong number — the hardest kind of error to notice. So a name that cannot be resolved stops the run, and that is enforced by the server, not left to the model's judgement: a program that catches the refusal and carries on anyway still fails.

Ask for the names back

For anything that matters, say "tell me which views you used". The resolver always knows, and a wrong table is the one error a sandbox cannot protect you from.

Searching every workspace costs a call each

View search looks in the workspaces whose names best match first, up to fifteen by default, and tells you how many of your total it covered. Because calls are rate limited, a full sweep of a large organization takes real time — about 90 seconds for 81 workspaces.

If a sweep runs out of time it says so rather than reporting that your data does not exist:

STOPPED: could not finish searching for "widget forecast". Covered 25 of 81
workspaces before the time budget ran out, so absence cannot be confirmed.
Ask the user which workspace it is in, then search that one directly.

Naming the workspace — "the profit table in ZIA Agent" — makes it exact, fast and cheap.

If your agent skips step 1 and writes code from memory, the call will usually fail with "not a function", and the error tells it to search first. That self-correction normally works; if it loops, say "search the API first" explicitly.

03Reading results without getting a wrong number

Two things about Analytics responses will silently produce a wrong answer if a program gets them wrong. Both were found running against a real organization, and the sandbox provides rows to handle both.

Export returns a flat array. The rows are in data directly, not data.rows:

const list = rows.of(out);        // right — handles every response shape
const list = out.data.rows ?? []; // wrong — undefined, so "no data"

Values come back formatted. "$1,682.39", "45%", "14 February, 2022" — all strings. Number("$1,682.39") is NaN:

rows.num('$1,682.39')                       // 1682.39
rows.sum(list, 'Sales')                     // { total, counted, skipped }
rows.groupSum(list, 'Region', 'Sales')      // { West: {...}, East: {...} }

sum and groupSum skip blanks and tell you how many they skipped, so an empty column is visible rather than silently counted as zero.

This is the failure mode to care about

On a real table of 755 rows, the correct code returns $1,299,947 across three regions. The same program written the obvious way returns { rowCount: 0, naiveSum: 0 } — not an error, just a confident report that you have no sales data. Nothing in the API signatures warns you.

04Worked example — a total across workspaces

> You: What were our East-region sales from July onwards, across every workspace?

The agent searches, then writes something like:

const CRITERIA = `"Sales"."Region"='East' and "Sales"."Date">='2026-07-01'`;
const ws = await za.getOrgWorkspaces({ 'ZANALYTICS-ORGID': ORG_ID });
const totals = {};

for (const w of ws.data.workspaces) {
  const views = await za.getViews({
    'ZANALYTICS-ORGID': ORG_ID, 'workspace-id': w.workspaceId, CONFIG: '{}',
  });
  for (const v of views.data.views.filter((v) => v.viewName.includes('Sales'))) {
    const out = await za.exportDataView({
      'ZANALYTICS-ORGID': ORG_ID, 'workspace-id': w.workspaceId, 'view-id': v.viewId,
      CONFIG: JSON.stringify({ responseFormat: 'json', criteria: CRITERIA }),
    });
    const list = rows.of(out);          // flat array, not out.data.rows
    if (list.length) {
      totals[w.workspaceName] =
        (totals[w.workspaceName] ?? 0) + rows.sum(list, 'Sales').total;
    }
  }
}

return { totals, grandTotal: Object.values(totals).reduce((a, b) => a + b, 0) };

One tool call. The response is a handful of numbers; no row ever reaches the model.

Large exports are asynchronous: start a job, poll until it finishes, then download. That is three operations and an unknown number of polls — painful one call per turn, trivial in a loop.

  'ZANALYTICS-ORGID': ORG_ID, 'workspace-id': wsId, 'job-id': job.data.jobId,

02What the sandbox cannot do

The isolate is a separate V8 heap with no host bindings except the operation bridge. These are absent, not merely discouraged:

typeof require          // "undefined"
typeof import           // "undefined"
typeof fetch            // "undefined"
typeof process          // "undefined"
typeof Buffer           // "undefined"
typeof XMLHttpRequest   // "undefined"

There is no filesystem, no child process, no socket, and no environment. The only reachable capability is za, carrying exactly the operations the server chose to expose.

This is enforcement, not instruction

The boundary is the isolate itself. It is not a system-prompt rule the model could be argued out of, and it does not weaken if the model is jailbroken — a jailbroken model simply has the same 76 read-only operations.

03Two ways to narrow the surface

Of 203 operations, 76 are exposed by default — every GET. The other 127 create, update or delete, and they are not present in the sandbox at all. A program that tries one gets not a function.

ZA_DOMAINS narrows it further, to any subset of the ten API domains. A deployment for analysts need not expose user management at all:

ZA_DOMAINS=data-operations,views-management,reports-dashboards   # 18 operations

Both filters are applied when the catalog is built, so an excluded operation does not exist inside the sandbox — this is not a check the model could talk its way past.

ModeOperationsCan it modify data?
Default76no

Enabling write operations

Think before you enable writes

With ZA_ALLOW_WRITES=true, a program can create, update and delete workspaces, views, rows and users. The sandbox stops code from escaping; it does not stop the model from being wrong. A misread prompt plus a loop can destroy a lot of data quickly, and there is no undo.

If you need writes, reduce the blast radius first:

  1. Use a dedicated Self Client with only the scopes you actually need, so the OAuth grant — not the flag — is the real boundary. Avoid ZohoAnalytics.fullaccess.all; see Which scopes.
  2. Point it at a non-production organization while you learn what your agent does.
  3. Use an Analytics user with limited permissions. The API can only do what that user can do.
  4. Keep the call budget low (ZA_MAX_TOOL_CALLS=25) so a runaway loop stops early.

04Where credentials live

Your client ID, secret and refresh token go into your operating system's keychain — macOS Keychain, Windows Credential Manager, Linux Secret Service — put there once by za-codemode login. Your agent's configuration holds no secret, only the command to run. The server reads the credential at startup, exchanges the refresh token for an access token, and keeps that token in memory. See Credentials & profiles.

The access token is never passed into the sandbox. It is substituted into the request templates in the host process, after the sandbox has handed over the call. Code in the isolate cannot read it, log it, or return it.

If you set credentials by environment instead

ANALYTICS_* variables and ZA_CREDENTIAL_COMMAND are supported for containers and CI, and they take precedence over the keychain. A refresh token in a config file or a shell profile is plain text that does not expire: do not commit it, do not paste it into a chat, and use a Self Client created specifically for this tool so it can be revoked without affecting anything else.

07For your security review

Points a reviewer usually wants:

  • Execution is local. The server runs on the user's machine under their account. No Zoho-hosted component is involved, and no data is routed through Zoho's agent infrastructure.
  • Network egress from the sandbox is zero. The isolate has no networking primitives. All API traffic originates in the host process.
  • Authorisation is the user's own. The tool can only reach what the configured OAuth grant and Analytics user permit. It adds no privilege.
  • The credential boundary holds under a compromised model. The worst a malicious or manipulated program can do is call exposed operations — which is the same set the user could call themselves.
  • There is an audit log. Outbound API calls are recorded by default; the detail stream, which includes the program that ran, is opt-in. Secrets are never written unless deliberately enabled. See Audit logging.
  • Revocation is the Self Client's. There is no central console to disable: access ends when the Self Client's grant is revoked in the Zoho Developer Console, or when the Analytics user's permissions change. Issue one Self Client per installation so that stays a per-user decision.

08What this does not protect against

Stated plainly:

  • A wrong answer. The sandbox guarantees safety, not correctness. A model can still filter on the wrong column or misread a date range. The one case that is guarded is substitution: a named variable, view, column or folder that cannot be resolved halts the run rather than being swapped for something else, and that is enforced outside the sandbox.
  • Data disclosure through results. Anything returned goes to your AI provider.
  • A compromised machine. The keychain unlocks with your login session, so anything running as you can read the refresh token. An attacker who does has your API access until the Self Client is revoked.
  • Prompt injection via data. If your data contains text crafted to influence a model, that text can reach the model through results. Returning aggregates rather than raw text columns reduces the exposure.

  4. Consider the model. A stronger model writes noticeably better code. This is the most common cause of poor results.

08Frequently asked questions

Q. Does this replace the Zoho Analytics MCP Server?

No. They complement each other: 26 named tools for single lookups, this for multi-step work. Install both. See the comparison.

Q. Does it reduce my API unit consumption?

No. The same operations are called, so the same units are billed. What it reduces is model turns and context — in a measured multi-workspace export, 19 model turns became 1.

Q. Do I need an OpenAI or Anthropic API key?

No. Your agent supplies the model. This server contains no AI.

Q. Where does my data go?

From Zoho Analytics to your machine, and from there only what the program returns goes to your AI provider. Nothing is routed through Zoho's agent infrastructure.

Q. Can I run it for my whole team from one place?

Not yet. Today each person installs it and stores their own credential, which also means each person's access is exactly their own Analytics permissions. A shared, multi-user deployment with browser sign-in is built but not released.

Q. Which operations are available?

All 203 from the v2 OpenAPI specifications; 76 read-only ones are exposed by default. Ask your agent to search — that is what search_analytics_api is for.

Q. Can the model see my credentials?

No. They stay in the host process and are substituted into requests after the sandbox hands over a call.

Q. Is there an audit log?

Yes. One line per outbound Zoho call is written by default; set ZA_AUDIT=full to also record the program each execution ran. Secrets are redacted, files rotate, and each line carries a hash of the previous one so edits are detectable. See Audit logging.

Q. Why does it need Node 20?

The sandbox is a V8 isolate from a native module that requires a modern Node. Older versions will fail to install it.

Q. Can I add my own operations?

Yes — point ZA_MANUAL_PATH at your own catalog, or regenerate the bundled one from the OpenAPI specs with npm run build:manual. See Operating.

02What UTCP is

UTCP — the Universal Tool Calling Protocol — is a JSON format for describing callable operations, plus client libraries that call them. A UTCP manual lists tools; each carries a name, a description, a JSON-Schema input and a call template saying how to make the HTTP request.

manual/analytics.utcp.json is exactly that: 203 operations, generated from the OpenAPI specifications published for the v2 API.

{
  "name": "exportDataView",
  "description": "Export Data from a View — Exports the data of a view...",
  "inputs": { "type": "object", "properties": { "...": {} } },
  "tool_call_template": {
    "call_template_type": "http",
    "http_method": "GET",
    "url": "${ZA_BASE_URL}/restapi/v2/workspaces/{workspace-id}/views/{view-id}/data",
    "header_fields": ["ZANALYTICS-ORGID"],
    "auth": { "auth_type": "api_key", "api_key": "Bearer ${ZA_ACCESS_TOKEN}",
              "var_name": "Authorization", "location": "header" }
  }
}
This manual is internal and is never published

UTCP has no token-refresh mechanism, which is why handing a manual to end users does not work — they would re-paste an access token every hour. Because ours stays inside the server, the server holds the credentials, mints tokens, and re-registers the manual when one rotates. Neither you nor the sandbox ever sees a token.

03What code mode is

Code mode is the pattern of letting a model write one program that calls many tools, instead of calling them one at a time. It is becoming standard: Anthropic ships it as programmatic tool calling, AWS as run_script, Snowflake as its Cortex code execution tool.

@utcp/code-mode is the implementation here. It takes the registered UTCP manual, generates a type-annotated signature per operation, and binds each one as a method on a za global inside an isolated-vm V8 isolate.

When the model's code calls za.exportDataView(...), that is not an HTTP request. It is a callback out of the isolate into the server process, which reads that operation's call template, substitutes the variables, and makes the real call. The isolate has no network of its own — see Security.

The program is plain JavaScript, not TypeScript

The signatures are type-annotated so a model can see each argument's shape, but there is no compiler anywhere in the chain — the code string goes straight into V8. A type annotation, an interface or an as cast is a syntax error, and V8's message never mentions types. The server detects that case and says so rather than passing the raw error back. Modern JavaScript is fine: async/await, optional chaining, destructuring, spread.

04Where the accuracy comes from

Signatures tell a model what it can call. They do not tell it that criteria strings follow a particular SQL-like grammar, that CONFIG must be stringified and URL-encoded, or that a bulk export is three calls and a poll. Those are the things generated code gets wrong.

So the OKF knowledge base ships with the server and is exposed as get_analytics_guide. Its source of truth is the published bundle at github.com/zoho/analytics-okf — npm run build:knowledge reads that repository's root manifest.json to resolve the current version, then its llms.txt link index, exactly as that repository instructs. 10Access tokens

You never handle these. The refresh token you stored is long-lived; the access token actually used on each call lasts one hour and the server manages it.

Minted fromyour stored refresh token
Lifetimeone hour, read from the response rather than assumed

Caching matters because a token would otherwise be minted afresh every time the process starts — and that happens more than you might think: restarting your agent, running status, or having two agent hosts configured. Measured on a real organization, a warm start reuses the cached token and skips the exchange entirely.

A cached token is only reused when it was minted by the same client ID against the same data centre, and has more than two minutes left. Change either and the cache is simply ignored rather than producing a confusing 8535. logout removes it along with the credential.

This mirrors what the Zoho Analytics CLI does — the same version envelope, credential binding, expiry skew and lifetime clamp — storing it in the keychain rather than an encrypted file, because the keychain is already there.

11Why not an encrypted file

It is the obvious suggestion, and it cannot work here. The MCP server is spawned by your agent with no terminal, so it can never prompt for a passphrase. That leaves two possibilities, and neither improves on the keychain:

  • The key sits next to the ciphertext. Anyone who can read one can read the other — encryption in name only.
  • The key sits in the OS keychain. Then the keychain is already doing the work and the file is an extra moving part protecting nothing further.

Hence the keychain itself.

12What this protects, and what it does not

Protects against: a config file read by another process or person, a screenshot, an accidental commit, a synced backup, a copied dotfiles archive.

Does not protect against:

  • Malware running as you. It can ask the keychain for the same entry your agent does. No user-session keystore defends against code already running as that user.
  • Results leaving the sandbox. Credentials never enter it, but whatever a program returns reaches your AI provider. See Security.
  • A leaked access token. It is a bearer credential for up to an hour. It is kept in the keychain, not a file, but anything that can read the keychain can read it.
  • A leaked refresh token. Zoho refresh tokens do not expire. If one escapes, revoke it in the Developer Console — logout removes only the local copy.

06Tamper detection

Each line carries a hash of the previous line from the same writer. Editing or deleting a line breaks the chain from that point, and audit reports where:

  integrity:
    api      1,284 lines, chain intact
    detail   BROKEN at line 412 — chain broken — a line was changed or removed

Chains are per writer, because one file legitimately holds lines from several processes: a local server is respawned every time you restart your agent, and two agent hosts can write at once. Each run verifies on its own, so restarts and interleaving are not mistaken for tampering.

What this does and does not prove

It detects edits and deletions by something that cannot rewrite the whole file. It does not stop an administrator who can. On a machine the user controls, local logs are useful for "what did my agent do" — they are not a compliance control. For that, get them off the host.

07Shipping them somewhere else

Point ZA_AUDIT_DIR at a directory your collector already watches, and the usual routes apply — Fluent Bit, Vector, a filebeat input, or a sidecar into your SIEM. Because the format is one JSON object per line with stable field names, nothing needs parsing rules:

Do not turn on ZA_AUDIT_STDOUT here

stdout is the MCP protocol channel for a stdio server. The setting exists for a server that does not speak MCP over stdout, and is ignored in this mode — see §3.

08What is still missing

Stated plainly, because a reviewer will ask:

  • No per-user rate limiting of Analytics calls. ZA_MAX_TOOL_CALLS is per program, not per user per hour.
